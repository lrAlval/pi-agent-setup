# Issues

Drive GitHub issues through a label-based lifecycle state machine. Pure `gh` CLI, no repo code changes.

Coexists with `triage`: triage owns triage roles and hands specified issues into this lifecycle (`status/ready` is the handoff target). This skill owns execution from there.

Every comment this skill posts **must** start with this disclaimer (same prefix as `triage`):

```
> *This was generated by AI during triage.*
```

## Reference docs

- [COMMANDS.md](COMMANDS.md) — per-command `gh` invocations (read before acting)

## Labels

States (exactly one per issue, created idempotently on first run):

- `status/backlog` — new, not yet specified (`B0365A`)
- `status/ready` — fully specified, claimable (`0E8A16`)
- `status/in-progress` — claimed, being worked (`1D76DB`)
- `status/in-review` — open PR linked to the issue (`5319E7`)
- `status/done` — manually confirmed or auto-set on merge (`006B75`)

Priorities (exactly one per issue, set at triage or anytime):

- `priority/P0` … `priority/P3` (`B60205`, `D93F0B`, `FBCA04`, `0E8A16`)

On first run in a repo, ensure all nine labels exist (`gh label create` if missing, never error on existing).

## State machine

| From → To | Driver |
|---|---|
| Backlog → Ready | dev/triage handoff, explicit `move` |
| Ready → In Progress | `claim` (sets assignee, records claim) |
| In Progress → In Review | auto: open PR linked to issue found during scan |
| In Review → In Progress | auto: new reviewer/owner comment on linked open PR (feedback scan) |
| In Review → Done | auto: linked PR merged (revertible via `move`) |
| Done (any ←) | dev-only manual `move`; never auto-entered otherwise |
| any → any | dev manual `move` (flag unusual, confirm, then apply) |

Unusual transitions (skip states, backwards moves, Done → anything, resurrecting Done): flag explicitly, require confirmation, then apply.

## Invocation

User invokes `/issues` with natural language. Interpret and act. Examples:

- "What's next?" → `next`
- "Claim #42" / "Claim #42 for @user" → `claim`
- "Move #42 to done" / "Set priority P1 on #42" → `move`
- "Bulk move in-review P1s to done — preview" → `bulk`
- "Run the feedback scan" → `scan`
- "Fix labels" → `fix-labels`

## Run order (every invocation)

1. **Ensure labels** exist (idempotent, silent unless creating).
2. **Feedback scan** (`scan` logic below). If it changed anything, report changes first — they affect `next`/`bulk` results.
3. **Hygiene check**: flag issues with zero or 2+ status labels, or zero or 2+ priority labels. Offer one-shot fix (`fix-labels`). Never auto-fix without confirmation; default priority on fix is `priority/P2`.
4. Execute the requested command.

Unlabeled new issues (no status label): flag, offer `move` to Backlog. Never auto-apply — respects triage flow.

## Commands

### next — ranked claimable work

Rank `status/ready` issues: `priority/P0` → `P3`, oldest first within tier (`createdAt` ascending).

Dependency deferral: if body matches `Blocked by #N` or `Depends on #N` (case-insensitive) and #N is not `status/done` (closed alone is not enough — check label), defer below all non-blocked issues and annotate `blocked by #N`. Chains resolve transitively; cycles flagged.

Output: ranked list, one line per issue: `#N | P1 | 12d old | title | blocked by #M (if any)`.

### claim #N [assignee]

1. Refuse if issue already `status/in-progress` (unless same assignee re-claiming — no-op) or `status/done`.
2. Assignee defaults to `gh api user --jq .login`. Set via `gh issue edit --add-assignee`.
3. Swap status label to `status/in-progress` (remove old, add new — atomic pair).
4. Post audit comment: `status: <Old> -> In Progress (claimed by @user, <ISO date>)` with disclaimer prefix.

### move #N --to <state> [--priority <P0..P3>]

Dev manual override to any state. Confirm first when unusual (see table). Applies label swap + audit comment `status: <Old> -> <New> (<reason>, <ISO date>)`. Optional `--priority` swaps priority label in same run.

`move` to Done is the only path into Done besides merged-PR automation.

### scan — feedback + merge scan (auto-runs, also standalone)

For each `status/in-progress` and `status/in-review` issue:

1. **Find linked PRs.** Two sources, no branch-name guessing:
   - Timeline cross-references: `gh api repos/{owner}/{repo}/issues/{N}/timeline` → `cross-referenced` events pointing at pulls.
   - Keyword search over open PRs: `Closes #N` / `Fixes #N` / `Resolves #N` in PR bodies.
2. **In Progress + open linked PR found** → move to In Review + audit comment `status: In Progress -> In Review (PR #X opened)`. Flag in output.
3. **In Review**: for each linked PR —
   - PR merged → move issue to Done + comment `status: In Review -> Done (PR #X merged)`. Flag.
   - PR open: read comments/reviews since last lifecycle comment (the last `status:` comment is the time cursor). New comment from anyone other than the PR author → move back to In Progress + comment `status: In Review -> In Progress (new feedback from @user on PR #X)`. Flag. PR-author-only comments are ignored.
4. Report-only when nothing changed: `scan: N in-progress, M in-review checked, no changes.`

Closed PR without merge: leave state, flag for human.

### bulk --op <set-state|set-priority|claim> --issues N,M.. | --filter [...] [--yes]

Selection: explicit `--issues 1,2,3` OR filter combo (`--state`, `--priority`, `--label`, `--assignee`). Both → union, deduped. Empty selection is an error, never "all issues".

Ops: `set-state --to <state>`, `set-priority --to <P0..P3>`, `claim [--assignee]`.

Dry-run preview is the default. Print table: issue | current → proposed | eligible?. `--yes` applies eligible only; conflicting/ineligible (already in target state, Done claim, ambiguous labels) are reported and skipped, never silently dropped. Each applied change gets its own audit comment.

### fix-labels

For each hygiene-flagged issue: show current labels → proposed fix (keep the single correct status/priority, default new priority `P2` only with dev acceptance). Apply on confirm. One shot, then re-run hygiene to prove clean.

## Audit trail

Every transition posts a short timestamped comment starting with the disclaimer, format `status: <Old> -> <New> (<reason>)`. The last `status:` comment doubles as the feedback-scan time cursor — never use bare `Updated:` text for this.
